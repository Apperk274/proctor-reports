Faster, Reliable Tests

The Unity test suite took about 11 minutes and failed a different handful of tests on every run. Now it takes about 5 minutes and passes cleanly. Two changes did it: saves retry when Windows briefly locks a file, and PlayMode tests run the game at 10x speed. UI timing now uses one clock, so the UI speeds up with the game.

The two problems

Slow: PlayMode ran in real time

The RoomHarness waits add up Time.deltaTime, and nothing set Time.timeScale. A test that waited for a bathroom trip or a walk to the door waited as long as a player would. At 1x, the scene tests for bathroom trips, departures and room layout took 33–96 s each.

Unreliable: "Unable to remove the file to be replaced"

Saves on Windows sometimes failed. Another process briefly opened a freshly written save without delete sharing, so File.Replace failed. That process was most likely Windows Defender's real-time scan. Nothing in the game overlaps its own file access.

The save fix

Product code, so players on Windows get it too. A shared FileRetry helper retries only genuine lock errors.

HRESULTMeaningRetried
0x80070020Sharing violationyes
0x80070021Lock violationyes
0x80070497ERROR_UNABLE_TO_REMOVE_REPLACEDyes
0x80070498 · 0x80070499ERROR_UNABLE_TO_MOVE_REPLACEMENTyes
—Read-only folder, disk full, file not foundfails at once

Up to 10 attempts, sleeping 10, 20, … 90 ms between them: about 450 ms at most, well over the 15–35 ms locks that were measured.

Game saves

  • The backup is never skipped. The primary is read through the retry before it becomes the backup, so a brief lock no longer drops the backup.
  • A primary that stays locked aborts the save. If the primary is still locked after every retry, the save stops and both files stay as they were.
  • A half-done replace is finished. If a replace fails with 0x498, the primary is already gone, and the next attempt moves the new file into place.

Settings saves

  • One retried atomic swap. Replace if the file exists, otherwise move, from a temp file with a unique name.
  • Load retries too. If the file stays locked, the game uses defaults for that session and holds back saves, so the player's real settings are never overwritten with defaults.
  • Leftovers are swept. Temp files older than 10 minutes are deleted on load.

Tests never write the developer's real settings or saves. Both are redirected to a test folder for every test.

10x game time in PlayMode

A test-only harness, GameTimeScale, started and finished by the PlayModeWatchdog hooks around every test. The game itself is unchanged.

Opting out

A fixture or a single test that must see real time says so with an attribute:

[GameTimeScale(GameTimeScaleAttribute.RealTime)]
public class CardAnswerTapTests

Pass and fail are the same at 1x and 10x. That was checked on full runs.

Why 10x and not 20x

ScalePlayModeResult
10x~190 s0 failed
20x (trial)194 s0 failed

20x passed too, but it was no faster. It also carries a real risk. At 20x, an ordinary 30–90 ms frame hitch becomes 0.6–1.8 s of game time, which is past the simulation's catch-up cap. Walkers would jump more than half a metre in one frame.

UiClock: one clock for UI timing

UI animations use real (unscaled) time on purpose, so they don't follow game speed. At 10x, that left the UI waits in tests at real speed: the payday count-up, the hub crossfade and the admission stamp.

  • One clock. All UI timing goes through UiClock: 26 reads in 18 files.
  • No change in the game. In the game, UiClock is exactly Unity's unscaled clock, so players see no difference.
  • Tests set its speed. Tests set UiClock.Speed to the game scale. Each frame, it advances by exactly the same clamped step as game time.
  • A guard test keeps it that way. It fails if UI code reads Unity's real-time clocks directly: unscaledDeltaTime, unscaledTime, realtimeSinceStartup, WaitForSecondsRealtime and the others. The exemptions are the frame pacer, the frame probe, audio and two single lines.
  • Gain: about 30 s per PlayMode run, from 219 s to about 190 s. The admission stamp fixture dropped from 6.6 s to 0.7 s, payday from 17.3 s to 8.5 s and hub navigation from 17.7 s to 7.6 s.

Tried: Time.captureDeltaTime

Unity can step every frame by a fixed amount of game time. A probe test checked whether that could replace UiClock. It can't.

  • Scaled time is exact. It advances by capture × timeScale every frame.
  • Unscaled time ignores the setting. unscaledDeltaTime and unscaledTime keep tracking the wall clock: 0.1–0.5 ms per frame in the probe. A fixed step can't speed up UI time, so UiClock stays.
  • Side finding: a fixed step ignores Time.maximumDeltaTime.

How tests are run now

  • Every Unity batchmode run has a hard timeout that kills it: 15 min for PlayMode, 6 min for EditMode. This rule was added after one run hung for 4 hours on an experimental watchdog change.
  • Routine work runs EditMode once, PlayMode on the affected fixtures, then the full suite once.
  • No blind experiments on test infrastructure.

Open

  • The 1x opt-outs are now most of the PlayMode time. CardAnswerTap (~32 s), RequestCardTap (~23 s), WalkPath (~14 s) and Phase6Perf (~13.5 s) lead the run. A faster clock won't help them. Further gains would need these tests to model frame time differently.
